# TODO-08 — 大小混淆:填充量化到档位

> 状态:候选(可行性高,格式 v2 级小变更)
> 来源:PLAN.md 后续计划第 8 项

## 问题:现状是「精确泄露」而非「大致」

`cipherSize = 156 + 16n + origSize` 可反解出**精确明文长度**,空文件(172B)也可识别。唯一根本解是填充量化(size bucketing)。

## 方案:格式改动出乎意料地小

- **Meta 零改动**:`OrigSize` 语义不变(存真实值,本就在加密头里)
- 填充量 = `bucket(OrigSize) − OrigSize`,为档位函数的确定函数,读写两侧各自可算,无需存储
- 写侧 `Close()` 时把补零并入末块一起加密(块认证顺带保护填充完整性)
- 读侧交付时截断到 `OrigSize`;SHA 仍对真实明文计算;长度总校验改用 `bucket(OrigSize)`

## 版本与兼容

- `blobVersion` 升 2;读侧兼容 v1 公式,老 blob 照常解密
- 已上传的 v1 对象不会自动变安全(可选 `migrate` 重传,挂起)

## 档位表是开销旋钮

- 2 的幂(平均 ~25% 开销)
- 小文件细档 + 大文件 10% 阶梯(**≤10%**)
- 连带收益:上传时长也被模糊(传的是填充后大小)

## 默认值建议

默认开粗档(≤10%),做成设置项——带宽对坚果云类流量计费网盘是真金白银。

## 残余泄露(填充管不了)

- 文件个数
- 对象 mtime(网盘自记)
- index.enc 大小泄露索引规模(可顺带把备份填充到整 MiB 档)

## 实现量

crypto 层约 100–150 行 + 档位/截断/SHA 边界测试;独立小阶段,不混进 GUI 开发。
