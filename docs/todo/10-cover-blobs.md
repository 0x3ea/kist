# TODO-10 — 封面出库:引用入索引、字节走 blob 管线

> 状态:候选(建议与 Phase 7 懒加载设计合并做:一次 schema/远端布局变更,两处受益)
> 来源:2026-08 缩略图体积与封面语义推演

## 问题

- 封面字节存在索引库内(`PutThumbnail` 任意字节直入库)→ 库体积随文件数线性膨胀(1 万张 × 10KB ≈ 100MB),**每次全量同步都背全部封面**,哪怕只改一条备注
- 自动生成缩略图计入 revision → 批量导入 1000 张会把 revision 顶上去,逼出一次巨型备份(放大器),库从此只增不减
- 封面语义含**用户自定义**(不可再生内容),现状无区分——不可再生的用户数据躺在状态库里,性能问题升级为正确性问题

## 方案:一封面一 blob + 索引轻引用

封面在数据性质上是「小号文件」,享受文件的待遇:

- 封面 = 独立小 blob,复用全部现有管线:BlobWriter/BlobReader、随机名扁平远端布局、fileKey 派生、先传字节后写引用(防悬空)、并发/进度/取消、gc
- 索引侧只存:**封面 blob 引用 + `source`(derived/custom)标志 + 上传状态**(未 ready 的引用不可见),不再存字节
- **revision 规则**:设置/更换封面计入(用户编辑,与 SetNote 同级);自动生成不计入(拆掉放大器)
- **gc 分叉**:derived 封面无引用即可回收;custom 封面按用户数据保护(gc 前置检查来源标志)

### 数据三层归属原则(本项的设计依据)

| 层 | 内容 | 待遇 |
|---|---|---|
| 状态(index.db,LWW 裁决)| 引用、标志、备注 | 保持极小 |
| 用户内容(blob,可靠上传)| 自定义封面、文件本体 | 不可丢 |
| 派生缓存(blob/本地,尽力)| 自动封面 | 可丢、可再生、可回收 |

### GUI 封面 LRU 缓存

```
GetCover(fileID):
  1. 查 KIST_HOME/covers/<fileID> → 命中:直接返回(零网络)
  2. 未命中:远端拉封面 blob → 解密 → 写入缓存 → 返回
  3. 缓存超预算(默认 512MB–1GB,Settings 可配)→ LRU 淘汰
```

网格滚动并发预取一屏,与 Phase 7 懒加载设计咬合。

## 代价与缓解

- **远端对象数翻倍**(1 万文件 → 2 万对象挤在 `/kist/` 扁平目录)→ gc 从「每次全列」改为**定期对账**(孤儿只是占配额,不损正确性);远期可按随机名前缀分桶——不泄露信息,但需先修订 PLAN.md「远端布局永远扁平」约定,属有意破例
- **文件内容不做隐形缓存**(产品语义:明文只出现在用户指定处;安全语义:不明文散落)——高清查看走显式预览/下载

## 迁移

既有库内缩略图一次性导出为 blob 的 `migrate`(小工具或 CLI 子命令),导出后 VACUUM 回收库空间。

## 涉及模块

`internal/index`(thumbnails.go、schema 迁移)、`internal/remote`、`internal/transfer`(gc 分叉)、GUI(懒加载 + LRU)。

## 验收标准

- 出库后 index.db 体积与封面总量解耦;批量导入触发的备份不再包含缩略图字节
- gc 不回收有引用的 custom 封面;derived 无引用可回收
- LRU 淘汰后再次访问可从远端恢复;断网状态下浏览/搜索/备注照常(本地优先不受影响)
- 迁移前后新旧库内容一致(引用、来源、可显示性)
