# TODO-11 — 远端存在性探测 O(1) 化 + PROPFIND 代价核查

> 状态:候选(小,可随时插入)
> 来源:网盘官方文档「同一文件夹下文件较多时建议只挂载子目录」引发的核查(2026-08)

## 问题背景

网盘文档警告「同目录文件过多」性能退化,而 kist 远端 `/kist/` 正是随库增长到万级条目的扁平目录。核查结论:

- 日常链路(上传/下载/备份/恢复)**全部按精确名 PUT/GET,不遍历**,不受影响;「目录层级较深」那半个警告被远端扁平布局天然免疫
- 付「全列代价」(PROPFIND 返回整目录)的调用点只有两处:
  - `internal/transfer/gc.go:15` 孤儿对账——刚需,靠低频使用缓解(手动/定期)
  - `internal/remote/store.go:38` `KeyFileExists`——**为找一个文件列了整个目录**,处在 init/新设备检测路径上,代价随库线性增长

## 方案

1. `KeyFileExists` 改为对精确路径 **PROPFIND Depth 0**(或 GET 探测),O(全目录) → O(1);注意区分 404(不存在)与其他错误(网络/权限)
2. **实测网盘 PROPFIND 是否分页/截断**——有些消费级 WebDAV 静默只返回前 N 条;若截断,gc 会漏判孤儿,属正确性问题而非性能问题,需在 dav 层处理(分段列举或显式不支持告警)
3. 分桶(远端布局 v2)**不在本项范围**——量级触发条件与方案见 [TODO-10](10-cover-blobs.md)「代价与缓解」、[TODO-03](03-upload-resume-chunked.md)

## 验收标准

- `KeyFileExists` 不再触发整目录列举(httptest 断言请求为精确路径探测)
- 404 与网络错误的返回行为与现状等价
- 网盘实测结论(是否截断、多大规模开始明显变慢)回填到本文件
